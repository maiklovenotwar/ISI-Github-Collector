Purpose and Scope

This report documents the implementation of the procedure described in the academic methodology report A Country-Attributed Dataset of Public GitHub Repositories, Their Owners and Contributors. The chapters follow the order of that report, with two additions: chapter 2 gives an overview of the system, and chapter 12 describes the database structure. Each statement of the academic report can thus be traced to the scripts, rules, tables and database columns that produce it. The academic report states what the procedure does and what is known about its accuracy; this report states how it is done.

The description refers to the source code published at https://github.com/maiklovenotwar/ISI-Github-Collector (commit 6413244). Figures refer to the project database on 16 October 2026 unless another date is given; they are the same figures as in the academic report. Paths are given relative to the root of the repository. The project database is a MySQL 8.0 database; the automated tests use SQLite.

The matching of organizations to the Orbis company database is a separate workstream. Chapter 15 summarises its state; its procedure is documented in docs/methodology/orbis_enrichment.md.

The pipeline consists of independent scripts that are run one after another. Each script reads from and writes to the database and writes only its own columns, so that a later step does not overwrite the result of an earlier one. Table 1 lists the steps in the order of execution.

All data come from the public interfaces of GitHub. Table 2 lists the endpoints used.

The units of observation correspond to the tables of the database (chapter 12):

  • repositories: one row per repository, keyed by the numeric GitHub repository identifier.
  • contributors: one row per GitHub account, irrespective of its role, keyed by the numeric GitHub account identifier. The column type holds the account type reported by GitHub (User, Organization, Bot).
  • organizations: one row per organization that owns a collected repository, keyed by the same identifier.
  • repository_contributors: one row per repository and contributing account, with the number of commits.

Accounts are identified by their numeric identifier, which GitHub keeps when an account is renamed; the login is stored as an attribute. An organization that owns a repository has a row in organizations and a placeholder row in contributors, because repositories.owner_id refers to contributors. Chapter 8 states which of the two rows is used.

4

Definition of the Population

4.1 Search query

The population is defined by the query that repository_collector.py sends to the repository search. Two modes exist:

created:<start>..<end> stars:>=<minimum>                  (standard mode, --min-stars)
created:<start>..<end> stars:<minimum>..<maximum>         (star-range mode, --star-range MIN MAX)

Start and end are timestamps in ISO 8601 format with a resolution of one second. Results are requested with sort=stars and order=desc. The default minimum is 100 stars (--min-stars); the bounds of the star-range mode are inclusive.

4.2 Exclusion of forks

The search returns forks only when the query contains fork:true or fork:only; the query contains neither. The column repositories.fork is therefore False for every collected repository and does not indicate a missing value. scripts/diagnostics/count_excluded_forks.py estimates the size of the exclusion from the totals that the search announces with and without fork:only (Table 3).

4.3 Temporal reference

Each repository row carries the time of its retrieval (collected_at) and the star count at that time (stars_at_collection). A repeated retrieval overwrites both. The repository columns stargazers_count, forks_count and open_issues_count are states at retrieval; their history is not recorded. In the project database the 27,498,495 repositories were retrieved between 28 November 2025 and 18 January 2026; for 5,294,213 (19 per cent) collected_at is NULL, because they were stored before the column was introduced. Query 2 of scripts/diagnostics/methodology_checks.sql counts the retrievals per month.

5

Data Collection and Completeness

5.1 Division of the period

The search returns at most 1,000 results per query (GITHUB_MAX_RESULTS, default 1,000). repository_collector.py divides the requested time range into periods of 30 days (REPOSITORY_INITIAL_PERIOD_DAYS). The first page of each period states the number of matches (total_count). If it exceeds 1,000, the period is divided into n equal parts, where n is the number of matches divided by 1,000 (integer division) plus one, and the parts replace the period in the list of open periods. Each part is processed in the same way, including further division. Periods are closed intervals; two adjacent parts share their boundary second. A repository retrieved twice is stored once, because rows are written by repository identifier (upsert). GitHub resolves creation times to the second, so a period of one second cannot be divided further; if it holds more than 1,000 matches, the first 1,000 by stars are collected and the period is recorded as truncated.

5.2 Pagination and state

Each period is requested in pages of 100 results (GITHUB_PAGE_SIZE). After every page the progress is written to a state file (data/collection_state.json by default): the list of periods, the index of the current period, the current page and the parameters of the collection (mode, star range). An interrupted call with the same arguments resumes at the period and page at which it stopped. A call with other arguments starts a new collection only if the recorded one has finished; otherwise it is refused.

Search responses are cached on disk for 24 hours (CACHE_EXPIRY, default 86,400 seconds); a repeated request within that time returns the stored response, including its star counts.

5.3 Error handling

  • A search request is attempted up to three times, including after a network error or an exhausted rate limit. If it still fails, the collection ends with an error, the period remains open and the script exits with code 1. Invalid tokens end the collection at once.
  • If the retrieved repositories cannot be written to the database, the collection also ends with exit code 1, and the page is not counted as collected.
  • Text values longer than their column, such as a default branch name of more than 100 characters, are shortened to the column length and logged (_cut_to_column_length in repository_collector.py).
  • A response marked incomplete_results (the search exceeded GitHub's time limit) is logged and recorded in the state file; the missing matches cannot be recovered.

5.4 Audit log

Each finished period is appended to logs/collection_audit.jsonl with the number of matches announced, the number retrieved, the number written and the difference between announced and retrieved. scripts/diagnostics/summarize_collection_audit.py lists the periods in which fewer repositories arrived than announced or fewer were stored than retrieved. The announced total is documented by GitHub as an approximation; agreement with the collected number is therefore not proof of completeness.

5.5 Check of the result

Query 1 of scripts/diagnostics/methodology_checks.sql counts the repositories per month of creation, together with the counts by star class. On 13 October 2026 every month from January 2008 to December 2025 was present, and no month lay markedly below both of its neighbours. Among repositories created from January to July 2012, about 51,300 per month have fewer than five stars; from August to December 2012, about 17,900. The number with at least ten stars does not change (about 5,300 and 5,500 per month). The break coincides with the introduction of stars on GitHub in August 2012.

5.6 Defects of versions before 13 October 2026

Six defects of earlier versions could lose data without an error: failed searches were recorded as empty periods; the first part of a divided period was skipped in the standard mode; the star-range mode did not divide periods; errors while writing to the database were logged and ignored; a finished state file was resumed by the next call regardless of its arguments; and a collection resumed with --limit closed the open period after one page. In addition, repositories.organization_id was not set when a repository was stored from a search result. The monthly count above shows no gap that would indicate a loss in the project database. The defects are described in docs/methodology/repository_collection.md.

6

Account Information

6.1 Owners

owners/owner_processor.py stores the owner of each repository. An owner of type Organization is retrieved from GET /orgs/{org} and written to organizations; every owner, including organizations, receives a row in contributors. An owner already present in the database is not retrieved again. If the retrieval of an owner fails, the owner is treated as known for the rest of the run and the repository is stored without a new owner row; on 14 October 2026 no repository was stored without one. Organizations are looked up by login.

6.2 Profile enrichment

Two scripts fill the profile columns through the GraphQL API, each requesting 100 accounts per call.

  • scripts/enrichment/enrich_org_data_graphql.py selects organizations whose name, blog, email, location, created_at and country_code are all NULL and whose enrichment_checked_at is NULL. It fills only columns that are NULL and does not overwrite existing values.
  • scripts/enrichment/enrich_contributor_profiles.py selects accounts with enrichment_checked_at NULL, restricted by --scope to accounts that appear in repository_contributors (new), all others (gap) or both (all, default). It overwrites the profile columns with the values reported by GitHub. It starts one process per configured token (--shard-index, --shard-count); accounts are divided among the processes by their identifier.

Both scripts set enrichment_checked_at on every row for which GitHub gave a definite answer, including accounts that no longer exist and profiles without content. A row without a country can thus be attributed either to a profile that was never retrieved (enrichment_checked_at NULL) or to a profile without a usable location. If a request fails, the column remains NULL and the row is selected again by the next run.

6.3 Consistency of location and country

When a profile or an owner is stored again and the location differs from the stored one after normalisation, country_code and region are set to NULL (update_contributor and update_organization in database/database.py), so that the next geocoding run determines them anew. Rows affected before this rule was introduced were reset on 14 and 15 October 2026 with scripts/maintenance/reset_stale_countries.py, after a CSV backup to data/backups/, and geocoded again by 16 October 2026. The profiles of all user accounts were retrieved again between 28 August and 6 September 2026. No column records when a location or a country was determined.

7

Country Assignment for Accounts

7.1 Input and output

The input is the profile column location. scripts/enrichment/update_location_geocoding.py (implemented in cli/geocoding_command.py) selects the rows of contributors and organizations with a location and without a country code (all rows with --force) and writes country_code (ISO 3166-1 alpha-2) and region. A location that is not a place, or for which the geocoder returns no match, receives an empty string in country_code, so that it is not requested again; in analyses the empty string is treated as a missing value. On 16 October 2026, 35.7 per cent of the 9,034,973 user accounts and 33.3 per cent of the 735,242 organizations stated a location; of these, 95.7 and 93.7 per cent had a country (queries 3 and 4 of scripts/diagnostics/methodology_checks.sql).

7.2 Order of resolution

geocoding/geocoding_service.py resolves a location string in the following order. The first step that yields a result ends the procedure.

  1. Cleaning and normalisation (geocoding/normalization.py, preprocess_location). Additions without geographic meaning (remote, home office, anywhere and similar), URLs, e-mail addresses and brackets are removed; the string is lower-cased and whitespace is unified. A string that is empty afterwards has no country.
  2. Curated tables before the cache. If the table of special cases or the table of corrections assigns the string to a country, that entry is used and replaces a cache entry with another country. An explicit entry stating that a string has no country (for example World, Mars) also takes precedence over the cache.
  3. Cache. Otherwise a cached result for the same string is used. Cache entries written by a text rule or a table carry no coordinates; they are not used but determined again, so that a change of the rules also reaches strings that are already cached.
  4. Patterns for non-places. Strings that are a URL, a time zone, or consist only of emoji, digits or two letters are treated as not a place.
  5. Text rules (geocoding/heuristics.py, section 7.4).
  6. Nominatim (section 7.6).

Every result passes through the territory rule (section 7.5) before it is stored. The result is written to the cache together with its source (mapping, heuristic, nominatim, no_result) and the time (cached_at).

7.4 Text rules

The text rules are applied in this order: the name of a US state as the whole string, after a comma or as a separate word (60 names); a two-letter US state abbreviation at the end (55 abbreviations, including territories); one of 56 large US cities at the beginning; a country alias as the whole string; a two-letter country code at the end. Ambiguous endings are treated as follows (Table 5).

7.5 Territories

Nominatim reports Taiwan, Jersey or Greenland under their own code, but Hong Kong and Macau under China, Puerto Rico and Guam under the United States, and the French overseas regions under France. geocoding/territories.py assigns the territory's own ISO code whenever the region or a part of the address of a result carries the exact name of such a territory. The table covers 26 territories of China, the United States, France, the Netherlands, Australia and Norway, among them HK, MO, PR, GU, VI, RE, GP, MQ, NC, AW, CW and SJ. The rule is applied to results of every stage.

7.6 Nominatim

The remaining strings are sent to the Nominatim service of OpenStreetMap through the geopy library (geocoding/nominatim_client.py), with English output and address details, one request per second (geocoding/rate_limiter.py). The first result is used; its country code and region are stored. If the service does not answer (timeout, rate limit, service error), the request is repeated once after five seconds. If it still fails, nothing is stored, the row remains open, and the run ends with exit code 1.

7.7 Cache

The cache (data/cache/geocoding_cache.json) holds one entry per normalised location string, without an expiry date. scripts/diagnostics/inspect_geocoding_cache.py summarises it without sending requests. update_location_geocoding.py --retry-empty removes all entries without a country and processes the rows marked as not geocodable again; this option was not used on the project database. A random sample of 500 of the 74,032 entries without a country was sent to Nominatim again on 13 October 2026; 17 (3.4 per cent) then yielded a country, about five of them evidently wrong.

7.8 Validation against a reference list

The reference list tests/resources/geocoding_gold_standard.json contains 1,068 location strings with the expected country or the expectation that none applies. It was assembled from the most frequent strings (30 per cent), strings stratified by country (30 per cent), known problematic cases and a random remainder; during labelling the result of the procedure was shown as a suggestion. scripts/maintenance/benchmark_geocoding.py --no-cache runs the procedure on the list without the cache. 7.9 Review of stored results

On 15 October 2026 the cache (292,470 strings, 193,576 with a geocoder match) was compared with the stored locations, read-only. Three kinds of error were found:

  • Strings that name exactly one country were placed in another (2,688 strings, 11,027 rows; for example Istanbul/Turkey in Italy). They were found by searching each string for country names; strings in which a country name is part of a place name (New Jersey, London, Ontario; 543 strings) were excluded.
  • Strings that are not a single place received a country (continents, jokes, abbreviations matched to an unrelated place). The most frequent strings whose words do not occur in the geocoder's address were reviewed by hand.
  • The former rule for two-letter endings read state abbreviations as country codes. Compared with Nominatim results for the same strings it was wrong more often than right for several endings (PE in 1,089 rows against 37). The rule was changed as described in Table 5.

Strings of the first kind with at least three rows (377) and the most frequent strings of the second kind were reviewed by hand, which gave 399 entries in the table of corrections; a second pass over strings whose stored country differed from the cached one added 42. A general rule ("a separately written country name decides") was tested and rejected, because it also changed strings with several places. The affected rows were reset with scripts/maintenance/reset_stale_countries.py --write after a CSV backup and geocoded again. Without --write, the script reports the rows whose stored country no longer agrees with the current tables and rules; on 16 October 2026 three such rows remained. In total the country of 46,023 rows of contributors and 8,055 organizations changed: 29,608 and 5,372 to another country, 16,415 and 2,683 to none.

8

Country Attribution for Repositories

8.1 Counting rules

  • Organizations are counted and analysed through the table organizations.
  • Persons are the rows of contributors with type = 'User'.
  • Rows of contributors with type = 'Organization' are placeholders; they are not counted and their country is not used. On 16 October 2026, 735,205 organizations had both rows; for 118,490 of them only the row in organizations carried a country, for 398 only the placeholder, and for 64 the two differed (query 5 of scripts/diagnostics/methodology_checks.sql).
  • Rows with type = 'Bot' are not counted as persons.

8.2 Country of a repository

The country of a repository is the country of its owner, read from organizations when the owner's account type is Organization and from contributors otherwise:

SELECT r.id,
       CASE WHEN c.type = 'Organization' THEN o.country_code
            ELSE c.country_code END AS country_code
FROM repositories r
LEFT JOIN contributors c ON c.id = r.owner_id
LEFT JOIN organizations o ON o.id = r.owner_id;

The rule uses the account type rather than repositories.organization_id, which versions before 13 October 2026 did not set; on 16 October 2026 it was set for 1,271,265 of the 2,951,091 repositories owned by an organization (query 6). By this rule 12,558,621 of 24,547,404 repositories owned by users (51.2 per cent) and 1,263,438 of 2,951,091 repositories owned by organizations (42.8 per cent) had a country. The CSV export writes each table separately and does not apply the rule; it has to be applied in the analysis.

9

Web Domains as a Sensitivity Indicator

9.1 Derivation

enrichment/cctld.py derives a country from the column blog and from the column email. From the website, scheme, path, query, user information, port and a leading www. are removed; IP addresses yield no domain. From the e-mail address the part after @ is used; addresses of the form users.noreply.github.com and addresses with more than one @ are discarded. A domain is then evaluated by four rules, in this order (domain_to_country_code):

  1. Service domains. Domains of services used worldwide and their subdomains yield no country: linktr.ee, buymeacoff.ee, coff.ee, lin.ee, notion.so, youtu.be, the link shorteners rb.gy, short.gy and surl.li, and the hosting services sr.ht, self.so, free.nf and co.nf. A different domain that merely ends in the same letters, such as mynotion.so, is evaluated normally.
  2. Second-level country domains. 44 combinations such as co.uk, com.br or co.jp are mapped to their country.
  3. Generic and filtered endings. Generic endings (com, org, net, dev, app and others) yield no country, and so do 52 country-code endings that are used mainly without reference to the country: endings commonly used as generic (io, co, ai, me, tv and others), free or very cheap endings (tk, ml, ga, cf, gq, pw) and endings used mostly for word play (re, pm, tf, st, cx, ax, gs, yt, wf, tl, lc, ag).
  4. ISO validation. uk is mapped to GB; any other ending counts only if it is a valid ISO 3166-1 alpha-2 code.

If both columns yield a country and they agree, the source is recorded as both; if they differ, the website takes precedence (blog). The endings .rs and .is remain in use although they are frequent in word play; results for these countries should be read with caution.

9.2 Selection and validation

scripts/enrichment/enrich_cctld.py processes organizations by default and contributors with --entity contributors. It selects rows whose country_code and country_code_cctld are empty and which have a website or e-mail address; for organizations, country_code_orbis must also be empty. It writes country_code_cctld, cctld_source, cctld_enriched_at and cctld_run_id. Before writing, the script compares its result with country_code for all rows that have both, and stops if fewer than 80 per cent agree; it also lists the fifteen countries with the lowest agreement among those with at least 20 compared rows. With --recheck it recomputes all stored assignments with the current rules and writes only those that change. On 16 October 2026 the agreement was 95.6 per cent for 47,199 organizations and 89.3 per cent for 242,080 accounts. Queries 7 to 9 of scripts/diagnostics/methodology_checks.sql list the countries assigned by each source.

Contributor Networks

10.1 Procedure

scripts/collection/collect_contributor_network.py runs four steps for one range of star counts; each step is a separate script and can be run on its own (Table 8).

Table 8. Steps of the contributor collection
StepScriptSourceWrites
1scripts/collection/collect_repository_contributors.pyGET /repos/{owner}/{repo}/contributors with anon=truerepository_contributors
2scripts/collection/add_missing_contributors.pyrepository_contributorsnew rows in contributors (id, login, type); repository_contributors.contributor_id
3scripts/enrichment/enrich_contributor_profiles.py --scope newGraphQL APIprofile columns of contributors
4scripts/enrichment/update_location_geocoding.py --contributorsgeocodingcontributors.country_code, region

Step 1 selects the repositories with stargazers_count in the half-open range from --min-stars (inclusive, default 5,000) to --max-stars (exclusive) that have no row in repository_contributors yet; --force selects all of them. It requests up to --max-pages pages (default 20) of 100 entries. Rows are written with an upsert on the unique key (repository_id, github_login) in blocks of 500 (--flush-size) and carry the identifier of the run (run_id). Values longer than their column are shortened and logged. If a block cannot be written, its rows are written one at a time; a repository of which only some rows were written is listed in the log and completed with --force. Repositories for which GitHub returned an error are written to failed_repos_<run>.txt in the log directory. A lost database connection ends the run. Steps 1 and 2 use MySQL-specific statements and run on other databases only with --dry-run.

10.2 Identification of accounts

Entries returned with a login are matched to contributors by the numeric identifier (github_user_id equals contributors.id). Anonymous entries (commits whose author e-mail address is not linked to an account) are stored with is_anonymous set, without github_user_id, and with the substitute login anon:<e-mail or name>. Accounts of type Bot are stored in repository_contributors but receive no row in contributors in step 2.

11

Repository Activity Measures

scripts/enrichment/enrich_repository_stats.py selects repositories whose commits_count or pull_requests_count is NULL and requests, through enrichment/graphql_handler.py, the fields pullRequests { totalCount } and defaultBranchRef { target { history { totalCount } } } for several repositories per GraphQL request. commits_count is the number of commits on the default branch; pull_requests_count counts open, closed and merged pull requests together. The counts are written after each batch; a failed item is logged and does not abort the batch. The time of retrieval is not stored.

On 14 October 2026, 27,465,002 of 27,498,495 repositories (99.9 per cent) had both counts. For the other 33,493 GitHub returned no data, which the GraphQL API does when no repository exists under the stored owner and name (after deletion, renaming or a change to private). They are listed in the file of failed identifiers and selected again in every run. repositories.contributors_count is not collected and is NULL; until 14 October 2026 the script wrote 0 into it.

Limitations

The limitations stated in the academic report have the following technical causes.

  • Missing locations. About two thirds of the accounts leave location empty; such rows have no country_code.
  • Several places in one string. The procedure does not split a string; Berlin / NYC is resolved as a whole by Nominatim or not at all.
  • Residual geocoding errors. Strings that name a country but were placed in another and occur only once or twice (about 2,300 strings, 2,600 rows) were not reviewed. Wrong matches for strings without a recognisable country name cannot be found automatically. Of the 289,920 distinct strings in the cache on 13 October 2026, 74,032 had no country, among them 19,276 that contain a country name as a word but have no match as a whole.
  • No random accuracy sample. The reference list is not a random sample of accounts, and its labels were made with the result of the procedure visible.
  • States at retrieval. Star counts, fork counts and locations describe the time of retrieval; no history is stored, and no column records when a location was geocoded or when activity counts were retrieved.
  • Contributor lists. Only the first 500 author e-mail addresses are linked, at most 2,000 entries per repository are requested, and bots are recognised by account type only.
  • Search totals. The totals announced by the search are approximations, and incomplete search answers cannot be recovered.
15

Outlook: Orbis Matching

scripts/enrichment/orbis_matching_pipeline.py matches organizations to entities in the Orbis database (Bureau van Dijk) by web domain and, as a fallback, by name, and writes the country of the matched entity to organizations.country_code_orbis together with a row in orbis_enrichments. When several candidates remain, an entity is chosen only if its country or its website corroborates it. The matching has not been run on the project database, and no accuracy estimate is available. A validation protocol with a stratified random sample, blind annotation and an acceptance criterion fixed in advance (docs/methodology/manual_validation.md) must be met before the Orbis country is used. Orbis data are licensed and not part of the public repository. The procedure and its terminology are documented in docs/methodology/orbis_enrichment.md and CONTEXT.md.
