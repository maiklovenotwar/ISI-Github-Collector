Methodology Report

A Country-Attributed Dataset of Public GitHub Repositories, Their Owners and Contributors

This report describes the construction of a dataset of public software repositories hosted on GitHub, the accounts that own them and, for repositories above a popularity threshold, the accounts that contributed to them. The principal analytical variable is a country for each account and, derived from the owner, for each repository. Countries are inferred from the location that account holders state voluntarily in their public profiles. The report defines the population of repositories, describes the retrieval procedure and the measures taken to ensure completeness, explains how free-text locations are converted into countries, and reports the results of the validation exercises. It closes with the limitations that remain and should accompany any analysis based on the data. Technical details of the implementation are documented separately in a technical methodology report.

1

Introduction

Open-source software is developed in public repositories, most of which are hosted on GitHub. The geographic distribution of this activity is of interest for research on innovation, digital sovereignty and international collaboration, yet GitHub does not record where a repository or its developers are located. The dataset described here addresses this gap by attributing a country to accounts and repositories on the basis of information that account holders publish themselves.

The report is intended for readers who use the data rather than the software that produced it. Each section states what a step of the procedure does, which information it cannot capture, and what is known about its accuracy. Figures refer to the state of the project database on 16 October 2026 unless another date is given.

A separate workstream links organisations on GitHub to company records in a commercial firm database. It is not part of the dataset described here; Section 13 gives a brief outlook.

2

Data Source and Units of Observation

All data are obtained from the public interfaces of GitHub. Three units of observation are distinguished:

  • Repositories: public software projects, each owned by exactly one account.
  • Accounts: personal user accounts and organisation accounts. An account enters the dataset either as the owner of a repository or as a contributor to one.
  • Contributions: the relation between a repository and an account that committed code to it, together with the number of commits.

Accounts are identified by the numeric identifier that GitHub assigns and that remains stable when an account is renamed. Automated accounts that GitHub labels as bots are retained in the data but are not counted as persons.

3

Definition of the Population

3.1 Inclusion criteria

The population consists of public repositories that are not forks, that were created within a chosen period, and that had at least a chosen number of stars at the time of retrieval. Stars are a lightweight form of endorsement by other users and serve as a common, if imperfect, indicator of attention. The population is thus defined by the query submitted to GitHub's repository search rather than by a sample drawn from it.

3.2 Exclusion of forks

A fork is a copy of a repository created under another account, usually in order to propose changes to the original. Most forks carry no independent development and would, if included, count the same project several times. The size of the exclusion depends on the star threshold, as Table 1 shows: at low thresholds forks are numerous, while among repositories with at least 1,000 stars they amount to about one per hundred.

3.3 Temporal reference

The dataset is not a snapshot taken on a single day. Each repository carries the time of its retrieval and its star count at that time. The 27,498,495 repositories in the project database were retrieved between 28 November 2025 and 18 January 2026, 16.8 million of them in December 2025. For 5,294,213 repositories (19 per cent) the time of retrieval was not recorded because they were stored before this information was collected.

Because membership depends on the star count at retrieval, a repository that reached the threshold only after its creation period had been retrieved is not included. This affects recent repositories most, as they had little time to accumulate stars: repositories created in December 2025 number 239,748, compared with about 310,000 per month earlier in that year. Comparisons over time should therefore end some months before the retrieval.

4

Data Collection and Completeness

4.1 Retrieval procedure

The GitHub search returns at most 1,000 results for any query. The collection therefore divides the period of interest into intervals of 30 days and subdivides any interval with more than 1,000 matching repositories until every part can be retrieved in full. Results are retrieved in pages of 100, and progress is recorded after each page so that an interrupted collection can be resumed without gaps or duplicates.

4.2 Safeguards against data loss

The procedure is designed so that errors become visible rather than silently reducing the data. A failed request is repeated; if it continues to fail, the collection stops and the affected interval remains open until it is retrieved successfully. An interval is never recorded as empty because of an error. For every completed interval, the number of matches announced by GitHub, the number retrieved and the number stored are recorded in an audit log. Text values that exceed the storage capacity of a field, such as unusually long branch names, are shortened and logged instead of interrupting the collection.

4.3 Assessment of completeness

The number of matches announced by GitHub is documented as an estimate, so agreement between announced and collected numbers is not by itself proof of completeness. As an independent check, the repositories were counted by month of creation. Every month from January 2008 to December 2025 is represented, and no month falls markedly below both of its neighbours, which would indicate a gap.

The monthly counts show one structural break. Among repositories created before August 2012, about 51,300 per month have fewer than five stars, compared with about 17,900 afterwards, while the number with at least ten stars remains stable. The break coincides with the introduction of stars in August 2012, when the earlier practice of “watching” a repository, which included the creator's own, was converted into stars. Counts of one or a few stars are therefore not comparable across that date.

Two further constraints of the source cannot be remedied by the procedure. A search that exceeds GitHub's internal time limit returns only the matches found so far; such incomplete answers are recorded, but the missing repositories cannot be recovered. In addition, if more than 1,000 matching repositories were created within the same second, only the first 1,000 by stars can be retrieved.

5

Account Information

Every repository has exactly one owner, either a personal account or an organisation. For each owner, the public profile is retrieved, including the self-reported name, website, e-mail address and location. An account is retrieved once and reused for all of its repositories.

The profiles of all personal accounts were retrieved again between 28 August and 6 September 2026 in order to update the stated locations. Whenever a stored location changes, the country derived from it is discarded and determined anew, so that every country in the data corresponds to the location stored alongside it. The location therefore reflects the place an account holder stated in autumn 2026 (personal accounts) or at the first retrieval (organisations), which is not necessarily the place at the time a repository was created.

6

Country Assignment for Accounts

6.1 Input data

The sole input for the country of an account is the free-text location field of its profile, for example “Karlsruhe, Germany”, “Bay Area” or “Earth”. The field is optional and unverified. About one third of the accounts complete it: 35.7 per cent of the 9,034,973 personal accounts and 33.3 per cent of the 735,242 organisations. Of the accounts that state a location, 95.7 per cent of personal accounts and 93.7 per cent of organisations receive a country; the remainder are entries that do not denote a place or that cannot be matched. The result is a country code according to ISO 3166-1.

6.2 Procedure

Locations are resolved in a sequence of stages, and the first stage that yields a result is decisive. First, curated tables of special cases and of manually reviewed corrections are consulted; an entry there always takes precedence, including entries that assign no country to a non-geographic string such as “World” or “Mars”. Second, results previously obtained for the same string are reused. Third, a set of text rules recognises country names, US states and large US cities. Finally, the remaining strings are submitted to an open geocoding service based on OpenStreetMap data, and the first match is used.

Territories with their own ISO code, such as Hong Kong, Puerto Rico or Réunion, retain that code. Ambiguous names are resolved by fixed conventions that are documented in the technical report; for example, “Georgia” without further qualification is read as the US state.

6.3 Validation against a reference list

The accuracy of the procedure was assessed against a reference list of 1,068 location strings, each labelled with the expected country or with the expectation that no country applies. The run reported in Table 2 was carried out on 16 October 2026 without reusing stored results.

The reference list is not a random sample of accounts. It over-represents frequent and known difficult strings, and the result of the procedure was visible to the annotators as a suggestion during labelling. The figures therefore describe the behaviour of the procedure on typical and difficult input; they are not an estimate of the share of accounts with a correct country.

6.4 Review of stored results

In October 2026 all 292,470 stored geocoding results were compared systematically with the locations in the database. Three types of error were identified: strings that name their country were placed in another one, strings that do not denote a place had received a country, and a rule for two-letter endings had read abbreviations of states and provinces as country codes. The frequent cases were reviewed manually and entered into the table of corrections, and the rule was revised. The affected records were reset and assigned a country anew. In total, the country of 46,023 personal accounts and 8,055 organisations changed: 29,608 and 5,372 respectively to another country, and 16,415 and 2,683 to none. Afterwards, apart from three records, no record remained whose stored country differs from the result of the current procedure.

7

Country Attribution for Repositories

Repositories have no location of their own. A repository is therefore attributed the country of its owner: for organisations the country of the organisation, otherwise the country of the owning personal account. A repository whose owner has no country remains without a country. By this rule, 12,558,621 of the 24,547,404 repositories owned by personal accounts (51.2 per cent) and 1,263,438 of the 2,951,091 repositories owned by organisations (42.8 per cent) have a country.

Counts of persons refer to personal accounts only, and counts of organisations to the organisation records. Where results refer to contributors, it is stated whether owners, contributors without own repositories, or both are meant.

The database holds up to three country estimates side by side: the country inferred from the stated location, the country implied by the web domain (Section 8), and, for organisations, the country of a matched company record (Section 13). Substantive results are based on the stated location alone, because it is the only source that is obtained in the same way for persons and organisations and that can yield any country.

8

Web Domains as a Sensitivity Indicator

For accounts without a location-based country, a country can be read from the country-code top-level domain of their website or e-mail address, such as .de or .co.uk. This information is used only to assess how sensitive results are to missing countries, not to fill the gaps. The reason is structural: generic domains such as .com, .org and .io yield no country and predominate in the United States, so filling gaps from domains would add almost exclusively countries other than the United States and bias the distribution.

Domains of global services (for example link-sharing or note-taking platforms), free domain endings and endings used mainly for word play yield no country. Where an account has both a location-based and a domain-based country, the two agree for 89.3 per cent of 242,080 personal accounts and for 95.6 per cent of 47,199 organisations. Agreement between two estimates is not a measure of the accuracy of either.

9

Contributor Networks

For repositories with at least 500 stars, the accounts that committed code to the repository are collected from GitHub's list of contributors, together with the number of commits of each. Newly encountered accounts are added to the account data, and their profiles are retrieved and assigned a country in the same way as those of owners. If a contributor list cannot be stored in full, the affected repository is identified and collected again, so that no repository is counted as complete with contributors missing. Three properties of the source limit the interpretation. First, GitHub identifies contributors by the e-mail address of the commit author and links only the first 500 addresses of a repository to accounts; the remaining contributors appear as anonymous. Anonymous relations, which make up 30 per cent of all relations, partly result from this limit, so the country composition of large repositories is known only for their most active contributors. Second, contributions are measured as commits; issues, reviews and discussions are not counted, and an anonymous author with several e-mail addresses is counted several times. Third, automated accounts are recognised only by their account type, so bots registered as ordinary users are counted as persons.

10

Repository Activity Measures

For 99.9 per cent of the repositories (27,465,002), the number of commits on the default branch and the number of pull requests were retrieved. The time of retrieval of these counts is not stored. The number of contributors per repository is not recorded as a separate variable; it follows from the contributor lists described in Section 9.

11

Quality Assurance and Reproducibility

All figures in this report are produced by read-only queries and scripts that are part of the published source code, so that they can be recomputed on the same data. Every correction that changed stored values was preceded by a backup of the affected records, and every corrected location string is listed, together with the assigned country and the reason, in a table that is published with the code.

In addition, the complete processing pipeline was executed end to end on a separate database with the same structure as the project database, populated with the 9,083 repositories created on 1 January 2026. The defects revealed by this test interrupted individual processing runs or affected exports and diagnostic tools; none of them altered stored values. They were corrected before this report was finalised, and a database built from the published code now has the same structure as the one from which the figures are taken.

12

Limitations

The following limitations remain after the corrections described above and should be stated wherever results by country are reported:

  • Selective disclosure. About two thirds of the accounts state no location. Whether these accounts are distributed across countries in the same way as the others is unknown.
  • Self-reported information. A stated location is unverified and denotes neither nationality nor the seat of an employer.
  • Several places in one entry. Entries naming more than one place are resolved as a whole or not at all.
  • Residual geocoding errors. Rare strings that name a country but were placed in another one were not reviewed (about 2,300 strings concerning about 2,600 accounts); incorrect matches for strings without a recognisable country name cannot be detected automatically.
  • Unmeasured overall accuracy. The accuracy for accounts as a whole has not been estimated. This would require a random sample of accounts labelled without knowledge of the procedure's result.
  • Popularity measures. Small star counts are not comparable across August 2012, and star counts describe the state at retrieval.
  • Contributor coverage. Contributor lists of large repositories are incomplete beyond the first 500 author addresses.
13

Outlook: Firm-Level Data

A separate workstream links GitHub organisations to company records in the Orbis database (Bureau van Dijk), using the organisation's web domain and, as a fallback, its exact name. This would add a further country estimate for organisations, based on a registered legal entity rather than a self-reported location, together with company attributes such as size and industry. As the matched entity may be a subsidiary, its country does not necessarily correspond to that of the headquarters.

The matching has not yet been applied to the project database, and no accuracy estimate is available. Before the firm-level country is used, a validation protocol based on a stratified random sample, blind annotation and an acceptance criterion fixed in advance must be met. Orbis data are subject to licence restrictions and are not part of the public repository. The results presented in this report do not use them.
