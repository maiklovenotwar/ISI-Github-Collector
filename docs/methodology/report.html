GitHub Collection Methodology

1

Purpose and scope

The collector builds a database of public GitHub repositories, the accounts that own them, and, for repositories above a star threshold, the accounts that contributed to them. Its main analytical product is a country for each account and, through the owner, for each repository. The country is derived from the location that an account states in its profile.

This report describes the procedure as implemented in the code at the data status given above. It is written for readers who do not work with the code. Each chapter states what a step does, what it does not capture, and what is known about its accuracy. Implementation details are given in collapsible notes and in the documents in docs/methodology/, which this report summarises.

The matching of organizations to companies in the Orbis database is a separate workstream and not part of this report; chapter 13 gives an outlook.

3

Population of repositories

The collector records public repositories that are not forks, that were created in a chosen time range, and that had at least a chosen number of stars when they were retrieved. The population is defined by the query sent to the GitHub repository search:

created:<start>..<end> stars:>=<minimum>

Forks are excluded

A fork is a copy of a repository under another account; most forks carry no development of their own. The search returns forks only when the query asks for them, and it does not. The size of the exclusion depends on the star threshold. Counts announced by the search on 2026-10-13:

Membership depends on the star count at retrieval

A repository that reaches the threshold only after its creation period was retrieved is not collected. Private and deleted repositories are not visible to the search.

Reference date

The collection is not a snapshot of one day. Each repository carries the time of its retrieval and its star count at that time. The 27,498,495 repositories in the project database were retrieved between 2025-11-28 and 2026-01-18, 16.8 million of them in December 2025. For 5,294,213 (19%) the time of retrieval is not recorded, because they were stored before the column existed. Two repositories were retrieved again on 2026-10-13.

Recent repositories are under-represented. A repository created shortly before its retrieval had little time to gather stars. Repositories created in December 2025 number 239,748, against about 310,000 per month earlier in that year. Comparisons over time should end some months before the retrieval.
4

Completeness of the collection

The GitHub search returns at most 1,000 results per query. The collector therefore divides the time range into periods of 30 days and divides any period with more than 1,000 matches further, until each part fits. It retrieves 100 results per page, sorted by stars, and records its progress after every page.

Measures against silent loss

  • A failed search request is retried up to three times. If it still fails, the collection stops with an error and the period stays open, so that a new call resumes there. A period is never recorded as empty because of an error.
  • Every finished period is written to an audit log with the number of matches GitHub announced, the number retrieved, and the number stored.
  • A state file belongs to one collection; a call with other arguments cannot resume someone else's collection by accident.

Limits

The announced total is approximate. GitHub documents the number of matches as an estimate, so agreement between announced and collected numbers is not proof of completeness.
GitHub may answer incompletely. A search that exceeds GitHub's time limit returns the matches found so far, marked as incomplete. Such answers are logged but the missing matches cannot be recovered.
One second cannot be divided. If more than 1,000 matching repositories were created in the same second, only the first 1,000 by stars are collected.

Check of the result

Counting the repositories per month of creation shows every month from January 2008 to December 2025, with no month markedly below both of its neighbours. The count shows one break: among repositories created before August 2012, about 51,300 per month have fewer than five stars, afterwards about 17,900, while the number with at least ten stars stays the same. The break coincides with the introduction of stars on GitHub in August 2012, when the earlier "watching" of a repository, which included the creator's own, was converted into stars. Counts of one or a few stars are therefore not comparable across that month.

Collections made with earlier versions

Before 2026-10-13 six defects could lose data silently, among them failed searches recorded as empty periods and a skipped first part of divided periods. The monthly count above found no gap that would indicate such a loss in the project database. The defects are listed in repository_collection.md.

5

Owners and their profiles

Every repository has exactly one owner, a user or an organization. The owner is stored in the table of accounts (contributors); an organization is in addition stored in the table organizations. An account is retrieved once; further repositories of the same owner reuse the stored row.

The profiles of all user accounts were retrieved again between 2026-08-28 and 2026-09-06, which updated the stated location. Whenever a stored location changes, the country derived from it is now cleared and determined again, so that a country always belongs to the location stored next to it.

The location belongs to the time of retrieval. It is the place an account holder stated in autumn 2026 (users) or at the first retrieval (organizations), not necessarily the place at the time a repository was created.
6

From a profile location to a country

The only input is the free-text location of a profile, for example Karlsruhe, Germany, Bay Area or Earth. It is optional and self-reported. About a third of the accounts state one: 35.7% of the 9,034,973 user accounts and 33.3% of the 735,242 organizations. Of those that state a location, 95.7% of the users and 93.7% of the organizations receive a country; the remainder are strings that are not a place or that the geocoder cannot match. The result is an ISO 3166-1 country code.

Procedure

A location is resolved in stages; the first stage that gives a result decides.

  1. Curated tables. A table of special cases (about 290 strings, 150 country names and aliases) and a table of 441 corrections, each checked by hand. An entry in these tables always decides, including an entry stating that a string has no country (World, Mars).
  2. Earlier geocoder results. Each distinct string is sent to the geocoder once; its answer is stored and reused.
  3. Text rules. US state names and abbreviations, large US cities, country names, and two-letter country codes at the end of a string. Endings that are both a country code and a state or province abbreviation (IN, CO, PE, PR) decide only after a known US place; otherwise the geocoder decides, so that Recife - PE is placed in Brazil, not in Peru.
  4. Geocoder. The remaining strings go to Nominatim (OpenStreetMap), one request per second; the first match is used.

Territories with their own ISO code keep it whatever the stage: Hong Kong is HK, Puerto Rico PR, Réunion RE. A location that is not a place, or that the geocoder cannot match, receives no country.

Conventions for ambiguous names

Georgia alone is read as the US state. A string ending in CA is read as California unless a Canadian city or province precedes it; it is not passed to the geocoder, which reads CA as Canada and placed Californian towns such as Tracy, CA in Canada in a trial. Strings ending in WA (Washington or Western Australia) go to the geocoder unless a known US place precedes them.

Check of stored geocoder results

On 2026-10-15 all stored geocoder results (292,470 strings) were compared with the locations in the database. Three kinds of error were found and corrected:

  • Strings that name their country were placed in another one: Istanbul/Turkey in Italy (989 accounts), China Beijing in the United States (677). Found by searching for exactly one country name that differs from the stored result; 2,688 strings with 11,027 accounts.
  • Strings that are not a place received a country: Mars in France (1,645 accounts), World in Switzerland and the United States, continents in Canada.
  • The rule for two-letter endings read state abbreviations as country codes. Compared with geocoder results for the same strings it was wrong more often than right, for example for PE in 1,089 accounts against 37. The rule was changed as described above.

The frequent cases were reviewed by hand and entered into the table of corrections; a general rule ("a separately written country name decides") was tested and rejected, because it also changed strings with several places such as Hamburg / Tokyo. The affected rows were saved, reset and geocoded again. Together with the reset of countries whose location had changed (chapter 5), the country of 46,023 rows in the table of accounts and 8,055 organizations changed: 29,608 and 5,372 to another country, 16,415 and 2,683 to none. Afterwards, apart from three rows, no row remained whose stored country differs from what the curated tables or the current rules give.

Country of an account and of a repository

What is counted

  • Persons are the accounts of type User. Bots are not counted as persons.
  • Organizations are counted from the table organizations. Their second row in the table of accounts exists only so that every repository can point to its owner, and is not counted.
  • The table of accounts contains owners and, since the contributor lists were collected, accounts that contributed without owning a repository. A statement about "contributors" names which group it means.

Country of a repository

A repository has no location of its own. It takes the country of its owner: for an organization the country from organizations, otherwise the country of the owning account. A repository whose owner has no country has none.

SELECT r.id,
       CASE WHEN c.type = 'Organization' THEN o.country_code
            ELSE c.country_code END AS country_code
FROM repositories r
LEFT JOIN contributors c ON c.id = r.owner_id
LEFT JOIN organizations o ON o.id = r.owner_id;

By this rule 12,558,621 of the 24,547,404 repositories owned by users (51.2%) and 1,263,438 of the 2,951,091 repositories owned by organizations (42.8%) have a country.

One source for results

The database holds three country estimates side by side: from the geocoded location, from the web domain (chapter 8), and for organizations from the Orbis company database (chapter 13). Results are based on the geocoded location alone, because it is the only source obtained in the same way for persons and organizations that can yield any country.

8

Web domains as a sensitivity analysis

For accounts without a geocoded country, a country can be read from the country-code domain of their website or e-mail address (.de, .co.uk). This source is used only to test how sensitive results are to missing countries, not to fill them, for a structural reason: generic domains such as .com, .org and .io yield no country, and they dominate in the United States. Filling gaps from domains would add almost only countries other than the United States.

Domains that belong to worldwide services (linktr.ee, notion.so, youtu.be), free endings (.tk, .ml) and endings used mostly for word play (.re, .ag) yield no country. Before they were excluded they accounted for about 5% of all assignments, among them most accounts assigned to Estonia.

Where an account has both, the two sources agree for 89.3% of the 242,080 accounts and 95.6% of the 47,199 organizations (2026-10-16; before the corrections of chapter 6, 88.4% and 93.7%). Agreement of two estimates is not the accuracy of either.

Contributors of a repository

For repositories with at least 500 stars, the accounts that committed to the repository are collected from GitHub's list of contributors, with the number of commits of each. New accounts are added to the table of accounts, their profiles retrieved and geocoded in the same way as owners. Accounts are identified by their numeric GitHub identifier, which stays stable when an account is renamed.

GitHub identifies contributors by the e-mail address of the commit author and links only the first 500 addresses of a repository to accounts; the rest appear as anonymous. No repository has 500 or more linked accounts. Anonymous rows (30% of all rows) partly result from this limit, so the country composition of large repositories is known only for their most active contributors.
Contributions are commits. Issues, reviews and discussions are not counted. Anonymous authors are counted by e-mail address, so one person with several addresses appears several times.
Bots are recognised by account type only. Automated accounts registered as ordinary users are counted as persons.
10

Repository statistics

For 99.9% of the repositories (27,465,002) the number of commits on the default branch and the number of pull requests (open, closed and merged together) were retrieved. The time of retrieval of these counts is not stored. The number of contributors per repository is not a column of its own; it follows from the contributor lists in chapter 9.

11

Limits that remain

The following limits remain after the corrections described above. They should be stated wherever results by country are reported.

  • Two thirds of the accounts state no location. Whether they are distributed across countries like the others is unknown.
  • A location is self-reported and unverified. It is neither a nationality nor the seat of an employer.
  • Several places in one string (Berlin / NYC) are resolved as a whole or not at all.
  • Rare geocoder errors remain. Strings that name a country but were placed in another and occur only once or twice were not reviewed (about 2,300 strings, 2,600 accounts). Wrong matches for strings without a recognisable country name cannot be found automatically.
  • The accuracy for accounts as a whole is not measured. It would need a random sample of accounts labelled without the procedure's suggestion.
  • Small star counts are not comparable across August 2012, and the star count is a state at retrieval.
  • Contributor lists of large repositories are incomplete beyond the first 500 author addresses.

Reproducing the figures

The figures in this report come from read-only queries and scripts in the repository:

  • scripts/diagnostics/methodology_checks.sql: repositories per month, share of accounts with a location and a country, country of repositories by the owner rule, countries from web domains.
  • scripts/diagnostics/count_excluded_forks.py: size of the fork exclusion.
  • scripts/maintenance/benchmark_geocoding.py: comparison with the reference list.
  • scripts/maintenance/reset_stale_countries.py (without --write): rows whose stored country no longer matches the current procedure.

Corrections that changed stored data were preceded by a CSV backup of the affected rows. The table of corrections, src/github_collector/geocoding/data/location_corrections.csv, lists every corrected string with the country and the reason.

13

Outlook: company data from Orbis

A separate workstream matches GitHub organizations to companies in the Orbis database (Bureau van Dijk), by web domain and, as a fallback, by exact name, and records the country of the matched entity. This would add a third country estimate for organizations, based on a registered entity rather than a self-reported location, together with company attributes such as size and industry. The matched entity can be a subsidiary, so its country is not necessarily that of the headquarters.

The matching has not yet been run on the project database, and there is no accuracy estimate for it. Every choice among several candidates needs a corroboration by country or website. A validation protocol with a stratified random sample, blind labelling and an acceptance criterion fixed in advance (manual_validation.md) has to be met before the Orbis country is used. Orbis data are licensed and are not part of the public repository. Results of this report do not use them.
